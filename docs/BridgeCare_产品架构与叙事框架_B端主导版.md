# BridgeCare — 产品架构与叙事框架（B端主导版）

> 方向确认：患者故事开场（A），双端产品产出（C），**B端顾问平台为主篇幅**
> 核心论点：患者体验差的根因，是顾问缺少好用、准确、高效的服务工具。解决顾问端，才能规模化地解决患者端。

### 第3页「问题转向」是叙事的关键转折点

这一页的作用是：**把观众的同理心从患者身上，转移到顾问身上。**

逻辑链条：

> 患者感到迷失 → 不是因为没人帮忙，而是顾问在救场 → 但顾问为什么救得这么辛苦？→ 因为他们没有系统支持 → **所以，要解决患者的体验问题，必须先解决顾问的工作流问题。**

这一页的配图建议是一张「顾问的人肉补丁图」：画一个顾问被各种工具（微信、电话、医院系统A、医院系统B、纸质单、Excel）包围，所有信息流都经过顾问一个人中转，顾问头上冒汗。

这句话可以作为这一页的标题：

> **"The coordinator is the system — but the system doesn't exist."**
> （协调者本身就是系统——但这个系统并不存在。）

## 第二部分：产品形态与架构（核心）

### 一、产品全景：一个引擎，一个界面

BridgeCare 的本质是一个**任务驱动的跨院就医协调引擎**。

```
┌─────────────────────────────────────────────────┐
│                 BridgeCare 引擎层                  │
│                                                   │
│   任务链引擎  ·  状态同步层  ·  知识库  ·  通知引擎  │
└──────────┬──────────────────────────┬─────────────┘
           │                          │
    ┌──────▼──────┐           ┌───────▼───────┐
    │  顾问工作台   │           │   患者APP      │
    │  (Desktop)   │           │   (Mobile)     │
    │  主角 · 复杂  │           │  配角 · 简洁   │
    └─────────────┘           └───────────────┘
```

**核心设计理念：**
- 顾问工作台是**发动机**：顾问在这里搭建任务链、处理异常、沉淀知识。
- 患者APP是**仪表盘**：患者看到的是顾问配置好的、被简化为"下一步做什么"的界面。
- 两者共享同一份任务数据——顾问更新状态，患者端自动刷新；患者完成签到，顾问端看板自动推进。
- **不是两个独立产品，而是一个系统的两个视图。**

### 二、顾问工作台（B端 Desktop）—— 信息架构

#### 顶层导航

| 模块 | 核心功能 | 顾问什么时候用 |
|------|---------|---------------|
| **工作台** | Kanban看板 + 今日待办 + 异常预警 | 每天打开第一个看的 |
| **患者管理** | 患者档案 + 任务链详情 + 沟通记录 | 处理具体患者时进入 |
| **任务模板库** | 可复用的转诊流程模板 | 新建患者任务时调用 |
| **知识库** | 医院信息 / 科室指南 / 多语言话术 / SOP | 需要查信息或配置模板时 |
| **数据中心** | 工作量统计 / 效率分析 / 异常复盘 | 周报/月报/管理汇报 |
| **设置** | 团队权限 / 通知规则 / 集成配置 | 管理员操作 |

#### 工作台详细设计（这是产品的灵魂）

工作台是顾问每天使用频率最高的界面，需要同时解决三个需求：
1. **总览**：所有患者现在到哪一步了？
2. **聚焦**：我今天需要做什么？
3. **救火**：哪些事情出问题了需要我介入？

**布局方案（三栏式）：**

```
┌──────────────────────────────────────────────────────┐
│  BridgeCare                          [搜索] [通知🔔3] │
├──────────┬───────────────────────────┬───────────────┤
│ 左栏     │  中栏（主区域）             │  右栏          │
│          │                            │               │
│ 今日待办  │  患者看板 (Kanban)          │  异常预警      │
│ ┌──────┐ │                            │  ┌─────────┐  │
│ │8件待办│ │  待启动  预约中  检查中     │  │报告超时   │  │
│ └──────┘ │  ┌──┐   ┌──┐   ┌──┐       │  │签到失败   │  │
│          │  │卡│   │卡│   │卡│        │  │预约取消   │  │
│ 筛选     │  │片│   │片│   │片│        │  └─────────┘  │
│ □ 紧急   │  └──┘   └──┘   └──┘       │               │
│ □ 英语   │                            │  快捷操作      │
│ □ B医院  │  报告待取  复诊中  已完成    │  + 新建患者    │
│          │  ┌──┐   ┌──┐   ┌──┐       │  + 新建模板    │
│          │  │卡│   │卡│   │片│       │               │
│          │  └──┘   └──┘   └──┘       │               │
└──────────┴───────────────────────────┴───────────────┘
```

**Kanban 卡片上显示什么（信息密度控制是关键）：**

每张卡片 = 一个患者的当前任务链快照：

```
┌─────────────────────┐
│ 🇺🇸 Sarah & Tom Hill │  ← 国籍flag + 姓名
│ 胎儿心脏超声 @B医院   │  ← 当前任务链名称
│                     │
│ ●○○○○○  Step 2/6    │  ← 任务进度条
│ ⏰ 预约截止: 今天 17:00│  ← 最近deadline（红色=紧急）
│                     │
│ 📋 需准备: 转诊单+保险 │  ← 当前步骤关键提醒
└─────────────────────┘
```

**为什么用 Kanban 而不是列表？（设计决策记录）**

| 维度 | Kanban | 列表 | 日历 |
|------|--------|------|------|
| 看到工作量分布 | ✅ 一眼看出哪列堆积 | ❌ 需要排序筛选 | ❌ 只看时间 |
| 发现瓶颈 | ✅ 某列卡片多=卡住了 | ❌ | ❌ |
| 看时间关系 | ⚠️ 需配合deadline标记 | ⚠️ | ✅ |
| 处理量大时 | ✅ 可拖拽+列内折叠 | ✅ 可滚动 | ❌ 拥挤 |

**决策：Kanban 为主视图 + 卡片上标 deadline + 顶部可切换列表/日历视图。**

### 三、任务链系统（核心创新模块）

这是整个产品最有设计含量的部分，也是作品集里最能体现"理清复杂问题"能力的模块。

#### 什么是任务链？

一次跨院转诊不是"一个任务"，而是一串有依赖关系的任务。比如"胎儿心脏超声转诊"包含：

```
确认转诊指征 → 查B医院号源 → 预约B医院 → 
发送患者准备须知(多语言) → 前一日提醒 → 
当日院内导航 → 签到确认 → 取报告 → 
报告转发A医院医生 → 安排复诊
```

**任务链模板 = 把这条链条固化成可复用的标准流程。**

#### 任务链模板的数据结构

每个任务节点包含：

| 字段 | 说明 | 示例 |
|------|------|------|
| 任务名称 | 做什么 | "预约B医院超声" |
| 执行者 | 系统 / 顾问 / 患者 | 顾问 |
| 依赖 | 前置任务 | "确认转诊指征"完成后触发 |
| 预计时长 | 用于排期 | 15分钟 |
| 截止规则 | 超时怎么办 | 4小时内未完成→升级预警 |
| 执行方式 | 自动 / 半自动 / 手动 | 半自动（引导式手动） |
| 所需文档 | 执行此任务需要的材料 | 转诊单、保险卡号 |
| 患者端通知 | 是否推送给患者 | 是（预约确认通知） |
| 通知语言 | 通知文案的语言版本 | 英语（可切换） |
| 异常处理 | 如果失败的备选方案 | 号源不足→推荐C医院 |

#### 任务链的可视化呈现

在患者详情页，任务链以**横向流程图**呈现：

```
  ✅        ✅        🔵(进行中)     ⬜        ⬜        ⬜
确认指征 → 查号源 →  预约B医院 → 发须知 → 前一日提醒 → 当日导航
  3min      5min      ⏰17:00截止    自动      自动      自动
```

- ✅ 已完成（绿色）
- 🔵 当前进行中（蓝色高亮）
- ⬜ 未开始（灰色）
- ⚠️ 异常（红色）

顾问可以：
- 点击任意节点查看详情
- 拖拽调整顺序
- 插入/删除节点
- 将当前节点指派给自己或同事

#### 模板库：知识沉淀的载体

**模板从哪来？**
1. 预置模板：系统根据常见转诊场景预置（产科、心内科、影像科等）
2. 顾问创建：顾问处理完一个新类型转诊后，可"保存为模板"
3. 团队共享：模板在团队内可见，可fork、修改、版本管理

**模板库的价值（这是你作品集里要讲清楚的"为什么"）：**

> 当前的问题：每个新顾问都要从头摸索"B医院超声怎么约、几点出报告、去几楼取"。这些知识存在于老顾问的脑子里、微信聊天记录里、便签纸上。
>
> BridgeCare 的模板库把这些隐性知识变成显性资产。一个新顾问入职第一天，打开模板库就能看到"胎儿心脏超声@B医院"的完整10步流程，每一步附带操作指引、注意事项、多语言话术。

**模板页面配图建议：**
- 模板库浏览页（卡片式，按医院/科室/复杂度分类）
- 单个模板详情页（任务链可视化 + 每步详情展开）
- 模板创建/编辑界面（拖拽式任务链搭建器）

### 四、跨院协调层（系统集成的现实处理）

这是体现你"尊重工程现实"能力的关键模块。

#### 现实约束

中国公立医院的系统大多**没有开放API**。你不能假装设计一个"一键预约所有医院"的系统——评审老师一看就知道是假的。

#### 解决策略：三层集成模型

```
┌─────────────────────────────────────────┐
│           Layer 3: API 直连              │
│  （有API的医院 → 自动同步状态/预约/报告）   │
│  覆盖率：约20%的 合作医院                  │
├─────────────────────────────────────────┤
│           Layer 2: 引导式手动             │
│  （无API但有在线系统 → 引导顾问操作+记录）  │
│  覆盖率：约50%                            │
├─────────────────────────────────────────┤
│           Layer 1: 结构化手动             │
│  （纯线下/电话 → 提供结构化录入+提醒）      │
│  覆盖率：约30%                            │
└─────────────────────────────────────────┘
```

**Layer 2「引导式手动」的设计示例——预约B医院超声：**

系统知道B医院没有API，但知道：
- 预约电话：xxx-xxxx-xxxx
- 需要提供的信息：患者姓名、护照号、转诊单号、检查类型
- 最佳拨打时间：工作日9:00-11:00
- 预计出报告时间：检查后2小时

所以系统不是让顾问"自己去想办法预约"，而是：

```
┌──────────────────────────────────────────┐
│  📋 预约 B医院 胎儿心脏超声               │
│                                          │
│  患者信息（已自动填充，可编辑）：           │
│  姓名: Sarah Hill                        │
│  护照号: P12345678                       │
│  转诊单号: REF-2024-0815                 │
│  检查类型: Fetal Echocardiography         │
│                                          │
│  [📞 一键拨打预约电话]                     │
│  最佳时间: 工作日 9:00-11:00              │
│                                          │
│  预约完成后请填写：                        │
│  预约日期: [____] 时间: [____]            │
│  科室位置: [____] 楼层: [____]            │
│  特殊要求: [____]                         │
│                                          │
│  [✅ 确认预约] → 自动通知患者 + 推进任务链  │
└──────────────────────────────────────────┘
```

**这个设计的价值：**
- 把"打电话预约"这件本来看不见的事，变成了一个有结构、有记录、可追溯的操作
- 顾问不需要自己组织要说什么（信息已填好）
- 预约完成后一键推进，自动触发后续任务（通知患者、设提醒）
- 这个过程的数据被记录下来，未来如果医院开放API，可以无缝替换为自动模式

**作品集里这一段非常重要——它展示你：**
1. 不画无法实现的饼
2. 在约束条件下找到优雅的解决方案
3. 设计了"从手动到自动"的演进路径

### 五、异常管理模块

跨院就医的常态就是"出意外"。好的系统不是消灭异常，而是**让异常被早发现、被有结构地处理**。

#### 异常类型与检测规则

| 异常类型 | 检测方式 | 响应级别 |
|---------|---------|---------|
| 预约超时未完成 | 任务deadline到期未推进 | ⚠️ 警告 |
| 患者未签到 | 预约时间+30min，APP无签到记录 | 🔴 紧急 |
| 报告延迟 | 超过预计出报告时间 | ⚠️ 警告 |
| 检查结果异常 | 报告中的关键指标标记（需医生确认） | 🔴 紧急 |
| 预约被取消 | 医院端取消通知/API回调 | ⚠️ 警告 |
| 患者长时间无响应 | APP通知后24h无打开 | ℹ️ 提示 |

#### 异常处理界面

异常预警出现在工作台右栏，按紧急程度排序。点击后展开处理面板：

```
┌──────────────────────────────────────────┐
│  🔴 Sarah Hill 未签到                     │
│  预约时间: 14:00 · 已过35分钟              │
│                                          │
│  可能原因:                                │
│  ○ 找不到科室  ○ 交通延误  ○ 取消未来      │
│                                          │
│  快速操作:                                │
│  [📞 联系患者]  [📞 联系B医院护士台]        │
│  [⏰ 重新预约]  [📝 标记为已处理]           │
│                                          │
│  处理记录:                                │
│  ___________________________________     │
│  [保存记录]                               │
└──────────────────────────────────────────┘
```

**设计要点：**
- 异常处理面板提供"可能原因"快捷选项，帮助顾问快速判断
- 所有操作一键可达（联系患者、联系医院、重新预约）
- 必须填写处理记录才能关闭异常——这既是复盘素材，也是知识库来源

### 六、知识库模块

知识库是模板库的"原料库"。模板是流程，知识库是信息。

#### 知识库内容结构

```
知识库
├── 医院档案
│   ├── B医院
│   │   ├── 科室分布（含楼层地图）
│   │   ├── 预约方式（电话/线上/现场）
│   │   ├── 报告领取（时间/地点/方式）
│   │   ├── 国际部信息
│   │   └── 特别注意事项
│   ├── C医院
│   └── ...
├── 检查/治疗指南
│   ├── 胎儿心脏超声
│   │   ├── 检查前准备
│   │   ├── 检查时长
│   │   ├── 报告解读要点
│   │   └── 常见异常及后续步骤
│   └── ...
├── 多语言话术库
│   ├── 预约确认通知（EN/JP/KR/...）
│   ├── 检查前准备说明
│   ├── 报告领取指引
│   ├── 异常情况沟通
│   └── ...
├── 保险与支付
│   └── 各医院接受的保险类型、支付方式
└── 文化注意事项
    ├── 各国籍患者常见顾虑
    └── 沟通偏好（如日本患者注重礼貌层级）
```

**知识库与模板的关系：**
- 模板中的每个任务节点可以"引用"知识库条目
- 比如任务"发送患者准备须知"自动调用知识库中"胎儿心脏超声>检查前准备"的多语言版本
- 顾问更新知识库 → 所有引用该条目的模板自动更新

### 七、患者APP（C端 Mobile）—— 配角但要精炼

患者APP的设计原则：**极简，因为复杂度已经被顾问端吸收了。**

#### 核心界面（只做3个主要页面）

**页面1：今天（Today）**
- 大卡片：你现在需要做的一件事
  - "下午2点，前往B医院3楼超声科签到"
  - 地址、导航按钮、预计时长
  - "我已到达"签到按钮
- 下方小卡片：明天要做的事（预览）
- 底部：一键联系顾问

**页面2：旅程（Timeline）**
- 竖向时间轴，展示完整任务链
- 已完成 / 进行中 / 待办
- 每个节点可展开查看详情
- 点击节点可查看相关文档（报告、转诊单）

**页面3：帮助（Help）**
- 常见问题（多语言FAQ）
- 一键联系顾问（文字/语音）
- 我的文档（所有报告、处方存档）

**患者APP的设计决策：**

| 决策 | 选择 | 理由 |
|------|------|------|
| 首页放什么 | "今天要做的一件事"而非任务列表 | 高焦虑场景下，信息越少越好。一次只看一步。 |
| 是否有自助预约 | 否，预约由顾问完成 | 医疗预约涉及专业判断，患者自助可能导致错误。APP是"被引导"而非"自助服务"。 |
| 是否展示全部任务 | Timeline页展示，但首页不展示 | 患者需要知道全貌（Timeline），但执行时只需聚焦当下。 |
| 联系顾问的入口 | 每个页面底部固定 | 安全感是核心需求。随时能找到人。 |

### 八、关键用户流程（作品集中用故事板呈现）

#### Flow 1：新患者入组（顾问视角）

```
顾问收到转诊通知 
→ 打开BridgeCare工作台 
→ 点击"+新建患者" 
→ 填写患者基本信息（姓名、国籍、语言、病情摘要）
→ 选择任务链模板：「胎儿心脏超声@B医院」
→ 模板自动生成10步任务链 
→ 顾问检查/微调任务链 
→ 点击「启动」
→ 系统自动：创建患者APP账号 → 发送邀请 → 推送第一条任务通知
→ Kanban上出现新卡片，状态为"待启动"
```

#### Flow 2：日常看板管理（顾问视角）

```
顾问早上打开工作台 
→ Kanban显示12个在管患者 
→ 右栏异常预警：2个紧急 + 1个警告
→ 先处理紧急：Patient X未签到 → 一键联系患者 → 确认迟到 → 通知B医院
→ 切换到"今日待办"：5件待办任务
→ 逐一处理：预约确认、报告转发、患者回复翻译
→ 每完成一件，Kanban对应卡片自动推进
→ 下午：Patient Y报告出 → 系统自动检测 → 顾问确认转发A医院医生
→ 下班前：今日所有待办清零 → 系统自动生成日报
```

#### Flow 3：异常处理（顾问视角）

```
系统检测：Patient Z的B医院报告超过预计时间2小时未出
→ 工作台右栏弹出⚠️警告
→ 顾问点击 → 查看详情：检查14:00完成，预计16:00出报告，现在18:00
→ 顾问点击"联系B医院" → 电话确认报告已出，系统未同步
→ 顾问手动录入报告信息 → 上传报告PDF
→ 系统自动：通知患者APP「报告已出」+ 转发A医院医生
→ 异常关闭，记录处理过程
```

#### Flow 4：知识贡献（顾问视角）

```
顾问处理了一个新类型转诊：「基因检测@C医院」
→ 该场景没有现成模板
→ 顾问从空白模板开始，逐步创建任务链
→ 每步关联知识库条目（C医院科室信息、基因检测准备事项）
→ 处理完成后，点击"保存为模板"
→ 填写模板名称、标签、适用场景
→ 模板进入团队模板库，其他顾问可使用
→ 未来同类转诊，一键调用
```

### 十、核心设计决策与权衡（作品集加分页）

这一页是评审老师最看重的——**不是你做了什么，而是你为什么这么做。**

#### 决策1：为什么是 Kanban 而不是工单列表？

> 顾问的心智模型不是"我有一个待办清单"，而是"我有12个患者，他们各自走到不同阶段了"。Kanban 的列对应阶段，卡片的位置本身就是状态信息。列表需要读文字才知道状态，Kanban 看一眼就知道。
>
> **代价**：Kanban 不擅长展示时间关系。**补偿**：卡片上标注 deadline，并用颜色编码紧急程度。

#### 决策2：为什么用任务链模板，而不是让顾问自由创建任务？

> 80%的转诊是可预测的流程（预约→检查→取报告→复诊）。如果每次都从零开始，既浪费顾问时间，也无法沉淀知识。模板让"个人经验"变成"组织资产"。
>
> **代价**：模板可能不覆盖所有场景。**补偿**：每个模板可完全自定义（增删改步骤），且"从空白创建"始终是可选项。

#### 决策3：为什么患者APP不让患者自助预约？

> 医疗预约涉及专业判断（选哪个科室、什么类型的检查、是否需要空腹等）。让外籍患者自助预约，出错概率高，出错代价大。BridgeCare 的理念是"顾问配置，患者执行"——复杂决策由专业人员完成，患者只需按指引行动。
>
> **代价**：患者无法自主操作。**补偿**：APP提供"申请变更"功能，患者可提出需求，顾问确认后执行。

#### 决策4：为什么保留人工介入，而不是全自动？

> 医疗场景是 high-stakes 的。错误的自动化（比如自动转发了错误的报告、自动预约了错误的科室）可能造成严重后果。BridgeCare 的自动化聚焦于"减少重复劳动"（通知、提醒、状态同步），而非"替代判断"。关键节点保留人工确认。
>
> **代价**：效率提升有上限。**补偿**：随着数据积累和信任建立，可逐步放开自动化范围。

#### 决策5：为什么不假装所有医院都能API对接？

> 中国医疗系统的现实是：大部分公立医院没有开放API。如果设计假装可以"一键对接所有医院"，评审老师（尤其有行业经验的）会立刻质疑真实性。BridgeCare 的三层集成模型（API/引导式手动/结构化手动）承认现实，并在约束中找到优雅解法。
>
> **代价**：手动步骤拉低自动化比例。**补偿**：引导式手动把"不可见的操作"变成"有结构、有记录的步骤"，本身就是价值。

## 第四部分：作品集文案模板

### 项目简介（150字版，用于作品集索引页）

> **BridgeCare** is a task-based coordination system designed for international patient referral in China's cross-hospital healthcare environment. Through shadowing medical coordinators and interviewing expatriate patients, I identified that the root cause of poor patient experience lies in the coordinators' fragmented workflow—juggling WeChat, phone calls, and disconnected hospital systems. BridgeCare redesigns the coordinator's desktop platform around patient task chains, with a companion mobile app that delivers step-by-step guidance to patients in their native language. The project demonstrates how solving the B-end workflow problem can scale to solve the C-end experience problem.

### 项目简介（中文版）

> **BridgeCare** 是一个面向中国跨院就医场景的任务导向型协调系统。通过跟岗医疗顾问和访谈外籍患者，我发现患者体验差的根因在于顾问端工作流的碎片化——他们在微信、电话和互不连通的医院系统之间疲于奔命。BridgeCare 以"患者任务链"为核心，重新设计顾问工作台，并配套极简患者APP，实现"顾问配置、患者执行"的协同模式。这个项目展示了：解决B端效率问题，才能规模化地解决C端体验问题。
